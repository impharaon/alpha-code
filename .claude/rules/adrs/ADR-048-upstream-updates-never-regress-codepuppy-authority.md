## 依据(owner 原话,2026-11-09,逐字)

1. 「界面当前的 alpha 才是唯一权威吧。」(`#1662` 评论 6736266548)
2. 「你应该了解opencode 更新后，哪些应该是权威，哪些应该是接受 opencode 的新增能力，并通过codepuppy 的接线与正确的方式集成，前端界面必须使用的是 codepuppy 的不应该使用opencode。」(`#1662` 评论 6736300635)
3. 「不可以因为 opencode 更新把经 codepuppy 拿回的唯一权威再封掉。」(`#1662` 评论 6736317973)
4. 「是否要有一个 adr runbook 来进行约束，下次不要犯这个错了，把codepuppy 唯一权威在 opencode 更新上游资源时，codepuppy 做唯一权威被回退。这是严格禁止的。」(编排器派发书转述;2026-11-09 核对时 `#1662` 评论里尚无此句)

## 背景

已有 ADR 逐项拿回过权威([[ADR-033]] 权限内核、[[ADR-035]] web search 失败面、[[ADR-038]] 审批期限、[[ADR-041]] 工具身份账本、
[[ADR-042]] OAuth 回环页品牌、[[ADR-043]] 住在上游目录里的自有文件),[[ADR-029]] 规定拿回时怎么接。但没有一条规则管
「**上游更新时这些权威还在不在**」:每项权威只由它自己那条 ADR 和那份接管清单守着,上游删文件、改接口、换代次时,
清单跟着文件一起消失,没有任何东西会变红。

`#1662`(换到 OpenCode 2)的方案里因此出现两种形态:其一,前端钉版改指引擎同一个上游 SHA、清空 Code Puppy 前端补丁
(方案基线 `docs/design/2026-11-08-1662-opencode2-generation-switch-baseline.md:44`、`:272`;整合分支上
`frontend/frontend-pin.lock:1` 当时为 `pin=33f94fce96…`,`origin/alpha` 上为 `pin=e11dbd0206…`);其二,
「先判能不能退回 L0」(清点表 `docs/design/2026-11-08-1662-opencode2-capability-inventory.md:115`、`:152`)被读成可以放弃权威。
接管清单的规模随换代从 49 条掉到 15 条(实测,2026-11-09):

```
$ git show origin/alpha:scripts/north-star-guard.sh > nsg.sh && bash nsg.sh --print-takeover | wc -l   # origin/alpha = e56ae0c036
      49
$ bash scripts/north-star-guard.sh --print-takeover | wc -l                                             # 整合分支 5cc6b9273d
      15
```

少掉的 34 条随上游文件删除而消失,其中承载的决定是否仍由 Code Puppy 握着,今天只能逐条人工追问。

## 决定 1 —— 适用范围

本 ADR 约束**每一次**上游进入 Code Puppy 的变更:每日同步(`sync-upstream.yml`)、受审上游集成(`ci.md` §4 第 3 条)、
依赖或上游版本升级、引擎换代([[ADR-037]])、前端钉版前移([[ADR-034]] 月更 bump)。没有「这次只是例行同步」的豁免。

## 决定 2 —— 三层权威

| 层 | 范围 | 上游更新时的规则 |
| --- | --- | --- |
| **Code Puppy 权威** | ① 全部用户可见界面:前端只用 Code Puppy 的界面,不用 OpenCode 的前端或桌面界面;用户看到的界面以当前正式版为准。② 产品决定:权限档位与审批、账户 / 计费 / 云能力准入、定制中心、品牌与文案、数据目录与凭据归属。③ **一切已从上游拿回的权威**:接管清单(`scripts/north-star-guard.sh` 的 `UPSTREAM_EXCLUDES`)、[[ADR-033]] / [[ADR-035]] / [[ADR-038]] / [[ADR-041]] / [[ADR-042]] / [[ADR-043]] 拿回的决定、`packages/ext` 与 `packages/ui-mac` 主进程握住的决定 | 由 Code Puppy 决定;上游更新只能改变「怎么握住」,不能改变「谁决定」(决定 3) |
| **OpenCode 权威** | 引擎内部:会话运行、模型请求、工具执行、MCP 运行时、存储与迁移、插件接口 | Code Puppy 消费它的决定,不手写替身(架构约束 K2) |
| **OpenCode 新增能力** | 上游这次新带进来的工具、开关、接口、界面 | 默认由 OpenCode 持有,Code Puppy 不为它建接缝、直接享用;只在交界处做最小的事:要在界面上出现 → 用 Code Puppy 的界面显示;新工具 → 在工具身份账本([[ADR-041]])登记;花钱或用凭据 → 经 Code Puppy 平台;上游实验开关 → 保持关闭,开哪一项由 owner 定 |

## 决定 3 —— 禁止回退

- 已拿回的权威**只许换接法**:可以沿 [[ADR-029]] 主权阶梯降到更轻的接缝(例如 L3 接管 → L0 插件钩子),**不许交回 OpenCode 默认**。
  「退回 L0」只指换更轻的接法,不指放弃权威。
- 上游删掉了承载某项权威的文件,这项权威不随文件消失:在新上游的对应位置重新拿回。
- 在新上游上握不住某项权威 → **停下,交 owner 裁决**;严禁静默放弃、严禁先合进去再说。
- 退役任何一项 Code Puppy 权威,必须有 owner 原话(带日期与出处),记进登记册(决定 4)。编排器、方案员、实现方、审计方都不能替 owner 退役。

## 决定 4 —— 机器拦截:Code Puppy 权威登记册 + 测试

- **登记册**:机器可读,由 `#1666`(换代 L4)交付;路径暂定 `docs/architecture/codepuppy-authority-registry.*`,L4 落地后回填实际路径。
  条目按「决定」立,不按文件立(文件会被上游删掉,决定不会)。每条至少写明:这项决定(人话)、属于决定 2 的哪一类、来源(ADR 或 owner 原话)、
  当前握法(阶梯级 + 机制所在位置)、守它的测试名、状态(在役 / 已退役 + owner 原话 + 日期)。
- **测试**判三件事,任一不满足即门红:
  1. **项不许消失**:与基线相比少了任何一条在役条目 ⇒ 红。条目只能改成「已退役」,不能删除;改成「已退役」而没有 owner 原话记录 ⇒ 红。
  2. **机制不许失效**:每条在役条目的测试必须带反向臂 —— 拿掉 Code Puppy 的机制、让上游默认接管,该测试必须红;没有反向臂的条目本身 ⇒ 红。
  3. **测试必须存在**:条目指向的测试找不到 ⇒ 红。
- 这道测试跑在本地门里;每日同步在打包候选 bundle 之前跑同一测试,不绿不推。

## 决定 5 —— 方案审与代码审

凡涉上游更新的方案与 PR,审查方按 runbook「审查拦截」一节逐项核对,PR 正文必须带「权威保持表」。出现以下形态的条目**直接拦**,不进入讨论:

- 前端跟上游同一个 SHA / 前端钉版改指新上游、清空或重生 Code Puppy 前端补丁而界面随之改变;
- 改用上游界面,或用户可见界面与当前正式版不一致且没有 owner 裁定;
- 某项 Code Puppy 权威「退回上游默认」/「交给 OpenCode」/ 从登记册或接管清单消失而没有新的握法和测试。

## 被否决的替代方案

- **只写进 ADR-047**:只管这一次换代,下一次同步或升版本不受约束,而回退恰好发生在「例行」的那一次。
- **只靠 runbook 文字、不加机器门**:这次的两个反例都是人在读方案时把文字读偏了;文字清单拦不住下一次误读。
- **拿接管清单(`UPSTREAM_EXCLUDES`)当登记册**:它按文件立、只覆盖 L2/L3;L0 插件钩子、主进程握住的决定不在里面,
  而且一项权威从 L3 换到 L0 时会表现为「从清单消失」,与放弃权威无法区分。
- **冻结整个引擎**:放弃全部上游修复与新能力,与「依据」第 2 条「接受 opencode 的新增能力」相反。

## 与既有 ADR 的关系

- [[ADR-029]]:阶梯仍是「怎么拿回」的唯一通道;本 ADR 加的是「拿回后不许交回」。
- [[ADR-034]]:钉版 + 补丁的机制不变;月更 bump 的产物受决定 2 第一类约束 —— 用户可见界面须与当前正式版一致,
  前移钉版而改变界面属决定 5 的拦截形态。
- [[ADR-037]]:换代的形状(独立票、能力清点、端到端判据)仍归它;本 ADR 给每次换代加一条不变量。
- [[ADR-047]]:其决策 1 中「前端投影 pin 在切换时与引擎是同一个 SHA」是决定 5 第一条拦截形态;其「精确接管面」一节是登记册在这次换代上的实例。
  与本 ADR 冲突的条文以本 ADR 为准。

## 后果

- ➕ 「谁决定」与「怎么接」分开:上游怎么变,只影响接法;权威的增减只能经 owner。
- ➕ 每日同步、升版本、换代走同一份检查,不再依赖读方案的人记得哪些是拿回来的。
- ➖ 每项在役权威都要有带反向臂的测试;登记册初建要把今天散在各 ADR、接管清单、ext 与主进程里的决定逐条收齐(`#1666`)。
- ➖ 上游删掉一项权威所在的文件时,同步会因测试红而停住,需要人在新上游上重新拿回;这是有意的代价。
- ⚠️ 登记册与测试落地前(`#1666` 合入前),决定 4 只能由 runbook 人工清单代行。
