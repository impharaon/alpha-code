# alpha-code#1662 补充 —— L3∥L4∥L5∥L6 开工前冻结的跨线接口

票:`#1662`(父)、`#1665` L3、`#1666` L4、`#1667` L5、`#1668` L6。M 级实施方案,补充已定稿的
[方案基线](2026-11-08-1662-opencode2-generation-switch-baseline.md)(下称「基线」)。路线、裁决都不改;
[裁决书](2026-11-08-1662-opencode2-rulings.md)、[清点表](2026-11-08-1662-opencode2-capability-inventory.md)、
ADR-047 也一字不改。读码时发现和它们冲突的地方,写在第 8 节「方案疑点」。

本文要做的事:基线 §4.1 第 409 行说「L3 与 L4 的接口在 L4 开工时先定函数签名」,这里把这件事提前到现在做,
并把读码找到的其它跨线接口一起定下。每个接口写清:谁实现、谁消费、落在哪个文件、TypeScript 签名、什么时候调用、
出错时怎么表达、哪条测试把它钉住。各 lane 内部怎么实现,本文不管。

## 0. 一页结论

1. **新定或改形的接口 10 条**(I1–I10,第 2、3 节),**原样冻结的既有接缝 4 组**(第 4 节)。两条以上 lane 都要改的文件,
   第 5 节给每个文件定了一个归属 lane。
2. **L3↔L4 的接口是一个函数,调用位置有两个**:`registerPolicy(context)` 由 ext 的 `setup` 第一句调用,它返回的 `seal()`
   由 `setup` 最后一句调用。L4 要往 2.x 插件 Context 上挂的东西全部经过它:执行闸、目录闸、Code Mode、权限评估、第一方 MCP、
   工具策略 RPC。代码落在 `packages/ext/src/policy/`,这个目录归 L4 独占(I3)。
3. **读码发现四件会让并行 lane 各写各的、或者让闸门变假的事**(都只读了代码,没跑):
   - 2.x 加载本地插件时,**每个 Location 各 import 一次**,URL 后面带一个递增的 `?__opencode_reload=` 参数。所以 ext 模块会被求值多次,
     而且没有一次和 sidecar 预载用的 URL 相同。今天「预载同一个 URL ⇒ 同一份调度器」这个假设(`sidecar.ts:155-158`)在 2.x 不成立(I2)。
   - 2.x 的执行闸住在 ext 里。**ext 在某个 Location 没装上,那个 Location 就没有执行闸**。v1 的闸在引擎核心里,ext 装不上也还在;
     基线的 S1 判据没有覆盖这种情况(I4,疑点 Q2)。
   - M0 会把「alpha 加在上游包里的 80 个文件」**全部移出**,其中 5 个是 ui-mac 和 ext 依赖的契约模块。L2 合入以后,
     这两个包按构造就编译不过,而且 L3/L5/L6 都依赖这 5 个模块(I6,疑点 Q1)。
   - renderer **今天就拿得到引擎口令**(`preload/types.ts:80-84`)。所以基线 S8「改指新接线」其实是 L5 和 L6 两边都要做的新工作(I8,疑点 Q4)。
4. **没有要 owner 拍板的项**。全部是整合分支内部可以回退的技术选择。需要编排器定的有 3 项:Q1、Q2、Q6。

## 3. 逐条接口

### I1 进程内引擎 fetch 的交接(L5 实现 → L3 消费)

**落点**:`packages/ui-mac/src/main/in-process-engine.ts`。Code Puppy 自有文件,L2 之后路径不变,**文件内容和签名都不改**。
发布点在 `packages/ui-mac/src/main/sidecar.ts`,今天是 `:153-154`。

```ts
// 不变
export type EngineFetch = (request: Request) => Response | Promise<Response>
export function publishInProcessEngine(fetch: EngineFetch): void
export function inProcessEngine(): EngineFetch | undefined
```

**冻结的语义**(和 v1 不同的地方):

1. **发布的是什么。** L5 发布的函数,是把 `start()` 的 `Transform` 拿到的 dispatch app 经 `HttpEffect.toWebHandler` 转成的 handler
   (`v2:packages/server/src/process.ts:40,50-55,71-75`;做法同 L1a 的 `docs/verification/2026-11-09-1662-l1/embed-entry.ts:45-55`)。
   L5 在外面再包一层,给每个请求补上 `authorization: Basic base64("opencode:" + password)`:dispatch 对每个请求都验 Basic
   (`process.ts:190,201-207`)。`toWebHandler` 的类型是 `(request: Request, context?) => Promise<Response>`
   (effect 4.1.0 的 `dist/http/HttpEffect.d.ts:107`,读自 L1a 装过的 `/private/tmp/ac1662-l1/oc2/node_modules/.bun/effect@4.1.0`),
   可以赋给 `EngineFetch`。
2. **ext 不再自己拼口令。** 也就是不再读 `OPENCODE_SERVER_PASSWORD` / `OPENCODE_SERVER_USERNAME`(今天在 `packages/ext/src/reload-scheduler.ts:37-38`)。
   这样 L5 就可以不把口令放进引擎进程的环境变量:放进去的话,引擎派生的每个 shell 和 MCP 子进程都会继承它。放不放由 L5 自己定。
3. **什么时候能取到。** L5 在 `Transform` 回调里**同步**发布。这一刻早于任何 Location 启动,也早于 ext 的 `setup`。
   ext 只能在 `setup` 里或之后调用 `inProcessEngine()`,不能在模块顶层调用,因为 sidecar 预载 ext 的那一次求值发生在 `start()` 之前(I2)。
4. **怎么指定 Location。** 用请求头 `x-opencode-directory: encodeURIComponent(directory)`(`v2:packages/server/src/location.ts:72-76`)。
   v1 用的 `?directory=` 查询参数,2.x 不读。
5. **出错时怎么表达。**
   - `inProcessEngine()` 返回 `undefined`(测试宿主,或者还没发布):调用方按「引擎不可用」处理。重载报 `waiting`「engine status unavailable」;
     识图、附件走今天已有的 fail-closed 分支。**不退回 TCP**:围栏会拒掉连自己回环端口的连接(L1a 勘破 §0 第 2 条、armB)。
   - fetch 返回非 2xx,当失败处理。启动期间返回的是 `503` 加 `retry-after`(`process.ts:229-242`)。
   - fetch 本身 reject,和非 2xx 同样处理。

**ext 要打的上游路由**(这部分归 L3,不算跨线接口,列出来是为了说明 L5 不用再提供别的东西):

- `GET /api/session/active` 取代 `/session/status`(`v2:packages/protocol/src/groups/session.ts:220`);
- `POST /api/location/reload` 取代 `/instance/dispose`(`v2:packages/protocol/src/groups/location.ts:51`);
- `GET /api/session/:sessionID/message`(`v2:packages/protocol/src/groups/message.ts:102`)。
- 列 provider、看 MCP 状态,可以直接用插件 Context 的 `provider` / `mcp` domain。它们在进程内直接调服务,不走 HTTP
  (`v2:packages/core/src/plugin/host.ts:53-80`)。

**钉住它的测试**:

- L5 写 `packages/ui-mac/src/main/sidecar-engine-host.test.ts`:
  - 「发布的 fetch 和监听端口是同一张应用图」:经它建一个会话,监听端口的 `/api/event` 能收到 `session.created`(判法同 L1a E2);
    反向臂:发布一个用 `ServerFetch.make` 另建的图,就收不到。
  - 「发布的 fetch 不用调用方给口令,`GET /api/info` 就返回 200」;反向臂:去掉包装层,返回 401。
- L3 用桩:`packages/ext/src/reload-scheduler.test.ts` 用一个假的 `EngineFetch`,断言请求头里有 `x-opencode-directory`、没有 `authorization`。

### I2 ext 的加载方式与进程级单例(L5 装载 ↔ L3 模块)

**事实(读码)**:2.x 用 `PluginModule` 加载本地路径的插件。路径指向文件时,经 `createPluginSources().read()` → `prepareSource()` 去 import,
URL 上会被加一个 `__opencode_reload=<递增号>` 参数(`v2:packages/plugin/src/source.node.ts:8-16,50`;`v2:packages/plugin/src/source.ts:13-39`;
`v2:packages/core/src/plugin/module.ts:129,174`)。`PluginSupervisor` 是 **Location 级**节点(`v2:packages/core/src/plugin/supervisor.ts:125,248`
`makeLocationNode`),每个 Location 各有一份 `createPluginSources`。由此推出两点:

- ext 的 bundle **每个 Location 各求值一次**;
- 这些求值**没有一次**和 sidecar 预载的 `pathToFileURL(extPluginPath).href` 是同一个 ESM 模块记录。

今天 `packages/ext/src/plugin.ts:37-47` 在模块顶层创建定制中心桥和重载调度器。到了 2.x,这会变成每个 Location 一份,parentPort 监听也会挂上好几次:
main 发来的一条重载请求,会被每份调度器各处理一次。

**冻结**:

- **L5 负责装载**:
  - 注入配置的 `plugins` 里写 ext bundle 的绝对路径,写成字符串项。不以 `-` 开头的字符串就是「加载」,target 是这个路径
    (`v2:packages/core/src/config/plugin/source.ts` 的 `parse`)。路径和今天一样,由 main 解析,经 `StartCommand.extPluginPath` 传进 sidecar。
  - sidecar 在 `start()` 之前照旧预载 `pathToFileURL(extPluginPath).href`(今天在 `sidecar.ts:159-164`)。
    理由没变:main 只在 ready 那一刻重发排队的重载代际,监听晚挂一步,那一批就丢了。
- **L3 负责模块**:
  - bundle 的 `default` 导出写成 2.x 的 promise 形状 `{ id, setup }`(`v2:packages/plugin/src/promise/plugin.ts:64-67`)。
    加载器只读 `default`(`module.ts:81-94`),其它命名导出不会被当成插件调用。
  - 进程级对象(定制中心桥 + 重载调度器)挂在 `globalThis[Symbol.for("codepuppy.ext.process")]` 上:第一次求值时创建,之后的求值直接复用。
    每个 Location 的 `setup` 只往调度器里**登记**本 Location;`setup` 返回的 `Cleanup` 负责**注销**。
    模块顶层不能再无条件执行 `createHubBridge(processParentPort())`。
  - 插件 `id` 由 L3 自己定。别的 lane 不靠 id 认 ext(I4 按路径认),所以 id 不冻结。

**钉住它的测试**:

- L3 写 `packages/ext/src/plugin-process-singleton.test.ts`:「同一个 bundle 以两个不同的 URL 求值两次 ⇒ parentPort 上只挂了一个 `message` 监听,
  一条 `codepuppy.reload.request` 只入队一次」。反向臂:把单例改回在模块顶层创建 ⇒ 两个监听,入队两次。
- L5:`packages/ui-mac/src/main/codepuppy-sidecar-wiring.test.ts` 里已有的接线锚,继续断言「import 引擎之前先预载 ext」。

### I3 工具策略挂进 ext(L4 实现 → L3 调用)

**落点**:`packages/ext/src/policy/`。这个子目录归 L4 独占,入口是 `packages/ext/src/policy/index.ts`。`packages/ext/**` 的其余部分归 L3。

为什么放在这里:清点表 K4 给的选法是「搬进 ext,还是作为 ADR-043 意义下的自有文件放进 2.x 包,由 L4 按『谁 import 谁』定」。
按这条判:2.x 下的执行闸、目录闸、Code Mode 处置、RPC 都要挂在插件 Context 上,唯一会 import 它们的是 ext;主进程只用到 I6 的契约类型。

```ts
import type { Plugin } from "@opencode/plugin" // promise 形状:v2:packages/plugin/src/promise/index.ts:3、plugin.ts:27-60

export interface PolicyRegistration {
  /** ext 的 setup 里最后一句调用:ext 自己的钩子和项目插件扇出都注册完以后,再注册执行闸在链尾的那一段。 */
  readonly seal: () => Promise<void>
}

export function registerPolicy(context: Plugin.Context): Promise<PolicyRegistration>
```

**调用时机**(L3 必须照做):

1. `setup` 的第一句是 `const policy = await registerPolicy(context)`;
2. 然后注册 ext 自己的钩子,跑项目插件扇出;
3. `setup` 的最后一句是 `await policy.seal()`。

**为什么要两个位置**:2.x 的钩子按注册顺序串行执行,大家改的是同一个事件对象(`v2:packages/core/src/plugin/hooks.ts:88-95`)。
`execute.before` 事件里的 `tool` 和 `input` 都可以被改写(`v2:packages/plugin/src/promise/tool.ts:39-46`)。

- 第一句给 L4 一个机会,在 ext 自己的钩子和项目插件扇出之前就拒掉调用。这保住了今天的不变量「deny ⇒ 零 hook、零副作用」
  (`packages/opencode/src/permission/codepuppy-tool-policy-gate.ts:15,194-205`)。只挂在链尾的话,被拒的调用会先流过项目插件的钩子。
  例外:插件按 `internal.pre`、按配置加载的包、`internal.post` 的顺序激活(`v2:packages/core/src/plugin/supervisor.ts:94-98`、`:146-147`),
  所以上游内置插件和排在 ext 前面的包,它们的钩子仍然先于 ext 运行。这些钩子要不要管、怎么管,属于 S1,由 L4 判定,不影响本接口。
- 最后一句让 L4 拿到所有改写之后的入参,对应今天 `confirm`「钩子之后、实现之前问」的语义(`:207-247`)。
- S1 的二选一(执行闸做链上最后一个回调,或者在它之后的任何改写都让调用被拒)仍由 L4 在 ADR-047 里定。两种做法都只用这两个位置。

**范围**:

- L4 要往插件 Context 上挂的**全部**东西都经过这一个函数:`execute.before` 执行闸;目录闸(`session.hook.context` 的工具表和 `tool.transform`);
  Code Mode 目录处置;`permission.hook.evaluate`;M2 第一方 MCP 声明用的 `mcp.transform`;I5 的 RPC。
- L3 和 L5 都**不写** MCP 配置里的 `codemode` 字段。S1 二选一里的 Code Mode 那一项,完全在 L4 内部做完。

**出错时怎么表达**:

- `registerPolicy` reject ⇒ ext 的 `setup` 原样 reject,不吞。这个 Location 的插件会被记成 failed(`v2:packages/core/src/plugin.ts:298-305`),由 I4 发现。
- `registerPolicy` 成功以后,ext `setup` 里任何**会因项目数据失败**的步骤(读项目配置、扇出项目插件),都必须就地吞掉并记日志,不能让 `setup` reject。
  理由:`setup` reject 会关闭本插件的作用域,连同已经挂上的闸一起撤掉(推断,见 Q2)。
- L4 的钩子要拒绝调用,就抛 `Tool.Error`。只有 `execute.before` 允许失败(`v2:packages/core/src/plugin/hooks.ts:23`)。

**钉住它的测试**:

- L4 写 `packages/ext/src/policy/register-policy.test.ts`:在 2.x 插件宿主里装一个只调 `registerPolicy` + `seal` 的测试插件,跑 `#725` 的 B 组。反向臂三条:
  ① 不调 `registerPolicy` ⇒ B 组红;
  ② 在 `seal` 之后再注册一个改写入参的插件 ⇒ 调用仍然被拒;
  ③ A 组同时断言 Code Mode 目录里也没有被拒的工具。
  这些都不依赖 L3 的进度。
- L3 写 `packages/ext/src/plugin-setup-order.test.ts`:用桩 `registerPolicy` 记下调用顺序,断言它是 `setup` 里第一个被 await 的、`seal` 是最后一个。
  反向臂:把 `seal` 挪到扇出之前 ⇒ 红。

### I4 ext 没装上时,sidecar 不报 ready(L3/L4 产出状态 → L5 判定;新增,需编排器确认,见 Q2)

**落点**:`packages/ui-mac/src/main/sidecar.ts` 的 ready 之前。数据来自 2.x 的 `GET /api/plugin`
(`v2:packages/protocol/src/groups/plugin.ts:10`,返回 `Location.response(Plugin.Info[])`)。

**L5 的判定**:初始 Location 预热完以后、发 `buildReadyMessage` 之前,经 I1 的 fetch 调 `GET /api/plugin`,请求头带 `x-opencode-directory: initialDirectory`。
在返回里找 `source.type === "local" && source.path === extPluginPath` 的那一项。

- 本地插件的 `source` 就是 `{ type: "local", path: target }`(`v2:packages/core/src/plugin/module.ts:62-63`),
  状态是 `{ status: "active" }` 或者 `{ status: "failed", error, ref }`(`v2:packages/core/src/plugin.ts:298-305`)。
- 找不到这一项,或者 `state.status !== "active"` ⇒ 发 `error` IPC 并 `exit(1)`。这和围栏装不上走同一条 fail-closed 路径(`sidecar.ts:188-191`)。
- `extPluginPath` 缺席时同样拒绝 ready:2.x 下没有 ext,就没有执行闸。
- 按路径认 ext,不按 id 认,所以 L3 的插件 id 不必冻结。同 id 的另一个插件先加载、导致 ext 被当成重复项丢掉的情况,也会表现为「找不到这一项」
  (`v2:packages/core/src/plugin/supervisor.ts:99-114`)。

**L3/L4 的义务**:就是 I3 那两条。`registerPolicy` 必须是 `setup` 的第一句;之后的步骤不能因为项目数据 reject。

**钉住它的测试**:L5 写 `packages/ui-mac/src/main/sidecar-ext-ready.test.ts`:
「`/api/plugin` 里 ext 是 failed ⇒ 不发 ready、发 error」「ext 那一项缺席 ⇒ 同上」「ext 是 active ⇒ 发 ready」。
反向臂:去掉这道判定 ⇒ 前两条红。

### I5 工具策略 API 走插件 RPC(L4 实现 → L5 调用;IPC 往 L6 那一段不变)
