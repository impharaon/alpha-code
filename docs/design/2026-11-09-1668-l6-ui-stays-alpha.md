## 0. 一页结论

1. **依赖清单规模:冻结界面打引擎的运行时调用点 170 个,分布在 45 个文件里**(`packages/app` 35 个、`packages/ui-mac/src/renderer` 10 个):
   v1 SDK 128 处 / 68 个方法,`packages/app` 自带的 1.17.13 版 v2 客户端 42 处 / 31 个方法;另有 7 个建客户端的点、1 处直连
   `fetch`、1 处 WebSocket 地址拼接、4 处事件流订阅、6 处 renderer 自己拿口令拼 Basic 头。类型层面 112 个文件 import v1 SDK 的类型
   (`app` 74、`session-ui` 13、renderer 25)。99 个方法里 84 个在 2.x 有对应端点(要转形状),1 个由事件派生,14 个在 2.x 没有对应(§1.7)。
2. **选定的适配做法(一句话):冻结界面整套原样留在 Code Puppy 自有路径、始终走它在 0.1.26 里实际跑的 v1 数据路径;
   在 renderer 里加一层 Code Puppy 自有的引擎适配器,把这条路径发出的每个 v1 请求和它要的 v1 事件流,按一张路由表翻成 2.x `/api/*`
   调用(经上游 `@opencode/client`),表外的请求响亮失败。** 适配器经冻结 app 早就留好的宿主接缝 `Platform.fetch` 接入
   (`alpha:packages/app/src/context/server-sdk.tsx:336-349` 全部经它建客户端),冻结代码只改 4 个文件、共几行(§2.4;第 4 个仅类型、运行时等价,编排器 2026-11-09 裁决 B1)。
3. **冻结界面不能放回 `packages/{app,ui}` 原位**:实测把 `alpha` 的 app/ui 清单放回 2.x 工作区,`bun install` 直接失败(§1.3,7 条
   `@opencode/{ui,app}@workspace:* failed to resolve` + 3 条 catalog 缺项 + 4 条 `@opencode-ai/*` 工作区依赖缺失)。所以 pin + SOT 补丁的
   **落点**从 `packages/{app,ui}` 改到 `packages/codepuppy-{app,ui}`(名字仍叫 `@opencode-ai/{app,ui}`,源码逐字不变),上游 2.x 的
   `packages/{app,ui,session-ui}` 原样留在原位、Code Puppy 不用。顺带:north-star 守卫的 carve-out ② 可以撤掉、每日同步不再还原前端。
4. **做不到「长相不变」的界面:2 条要 owner 定,3 条要 L6 第一步核实后才知道有没有**(§8)。要定的:U1 会话页的任务清单卡
   (2.x 的 todo 工具是实验开关,正式渠道默认关,不开就永远不出现);U2 侧栏项目列表里「打开过、但还没发过消息」的项目
   (2.2.6 没有项目端点,合成的列表里没有它)。待核的:上游组件里的 worktree / LSP 状态 / 改项目名(U4)、上游设置页的凭证增删(U5)、
   MCP「去授权」(U6)。分享对话已由 owner 裁决拿掉(R6)。
5. **方案疑点 4 条**(§9):最大的一条是 0.1.26 里冻结 app 有一半调用走的是 1.17.13 版 v2 客户端,打的是 1.x 引擎的 `/api/*`,
   而 2.2.6 删了其中 26 条路径;这部分形状漂移没有逐条实测,L6 第一步要先跑一次「表外请求清单」。

## 2. 选定方案

### 2.1 冻结界面的落点:Code Puppy 自有路径,原名,原字节

| 新路径(alpha 自有,`packages/*` 自动成为工作区) | 包名 | 内容来源 | 以后谁能改 |
| --- | --- | --- | --- |
| `packages/codepuppy-app` | `@opencode-ai/app` | pin `e11dbd02` 的 `packages/app` + SOT 补丁 = `origin/alpha:packages/app` | 只经 SOT 补丁(ADR-034 机制不变,落点换了) |
| `packages/codepuppy-ui` | `@opencode-ai/ui` | 同上,`packages/ui` | 同上 |
| `packages/codepuppy-session-ui` | `@opencode-ai/session-ui` | `origin/alpha:packages/session-ui` 逐字 | Code Puppy 自有代码 |
| `packages/codepuppy-sdk-v1` | `@opencode-ai/sdk` | `origin/alpha:packages/sdk/js` 逐字(只当 v1 类型与 v1 请求序列化用,不连任何 v1 引擎) | Code Puppy 自有代码;生成脚本不再跑 |
| `packages/codepuppy-core-util` | `@opencode-ai/core` | `origin/alpha:packages/core/src/util/{path,encode,binary,retry,array}.ts` 五个文件逐字 + 一个只导出 `./util/*` 的清单 | Code Puppy 自有代码 |

- 上游 2.x 的 `packages/{app,ui,session-ui,sdk}` 留在原位、逐字等于上游,Code Puppy 不 import 它们。
- 包名不改,冻结代码里的 580 + 41 + 120 处 import 一行都不用动;`@opencode-ai/*` 与 2.x 的 `@opencode/*` 是两个作用域,不撞名。
- `frontend/frontend-pin.lock` 写回 `pin=e11dbd02…`,`frontend/codepuppy-patches/codepuppy-frontend.patch` 取 `origin/alpha` 原样字节;
  补丁里的路径仍是 `packages/app/…`、`packages/ui/…`(相对 pin),**落点映射**由判据脚本做(§4 C1、§5)。

### 2.2 数据路径:始终走 0.1.26 实际跑的 v1 路径

- 冻结 app 探协议时由适配器回答 `GET /global/health`(取 2.x `GET /api/info` 的版本,回 `{healthy:true, version}`),
  于是 `detectServerProtocol` 照旧得到 `"v1"`,冻结 app 里 0.1.26 跑过的那一支原样执行;从没跑过的 v2 支路继续不跑。
- 理由:0.1.26 的长相 = v1 路径上的组件读 v1 形状的 store。冻结 app 的 v2 路径会让组件读另一套 store(`server-session.ts:204`
  `session_message`),renderer 时间线读的 `session().data.message/part`(13 处)在 v2 路径下不再被填;而且 v2 路径里有按协议切换的
  界面元素(`components/settings-providers.tsx:88,224`、`app.tsx:352-356`)。

### 2.3 引擎适配器(Code Puppy 自有,唯一咽喉)

**落点**:`packages/ui-mac/src/engine-adapter/`(L6 独占;实现时从 `src/renderer/` 下挪到它旁边 —— renderer 的
locale-regression 闸禁止 `src/renderer` 下出现任何 `OpenCode` 字样,而适配器必须引 2.x 客户端、夹具带真引擎文本;
仍经 `renderer/index.tsx` 打进 renderer 包)。依赖 `@opencode/client`(2.x 公开包,`promise` 入口)与
`@opencode-ai/sdk/v2` 的类型。

**形状**:一个 `engineFetch(input, init): Promise<Response>`,按「方法 + 路径模板」查一张路由表:

```ts
// engine-adapter/routes.ts(示意签名,不是实现)
type V1Route = { method: "GET" | "POST" | "PUT" | "PATCH" | "DELETE"; path: string }   // 例 { POST, "/session/{sessionID}/prompt_async" }
type Handler = (req: { params: Record<string, string>; query: URLSearchParams; body: unknown; directory?: string },
                api: OpenCodeClient /* @opencode/client */) => Promise<Response>
export const V1_ROUTES: ReadonlyArray<readonly [V1Route, Handler]>          // v1 SDK 发出的请求
export const V2_117_ROUTES: ReadonlyArray<readonly [V1Route, Handler]>      // 1.17.13 客户端发出的请求
```

- **请求的来路**:冻结的 v1 SDK 与 1.17.13 客户端照常把调用序列化成 HTTP 请求,只是它们的 `fetch` 换成 `engineFetch`。
  hey-api 的 `throwOnError`、结果对象、SSE 解析(`global.event().stream`)都由冻结的生成代码自己做,适配器只扮演「服务器那一侧」。
- **处理**:每个 handler 调一个 `@opencode/client` 方法,把 2.x 响应转成 v1 响应(类型取 `@opencode-ai/sdk/v2` 的生成类型,
  2.x 一侧取 `@opencode/client` 的类型 —— 两边都有编译期类型,2.x 改了形状 typecheck 就红)。
- **事件流**:`GET /global/event` 的 handler 返回一个 `text/event-stream` 的 `Response`,内容是 v1 `GlobalEvent` 帧,来源是 2.x
  `GET /api/event`。直通的:`permission.asked/replied`(2.x 同名,载荷按 I7a 映射回 v1 的 `permission/patterns/always/metadata/tool`,
  冻结 app 里已有同一个映射的反向写法 `server-sdk.tsx:28-46` 可对照)、`lsp.updated`、`project.updated`、`vcs.branch.updated`、`pty.*`、
  `server.connected`。派生的:`message.updated`、`message.part.updated`、`message.part.delta`、`message.removed`、`session.status`、
  `session.idle`、`question.*`(由 `form.*`)、`todo.updated`(仅当 todo 开关开,§8 U1)。消息派生规则:流式增量
  (`session.text.delta`、`session.reasoning.delta`、`session.tool.input.delta`)直接转成 `message.part.delta`;
  每个 `*.ended` / `session.tool.{success,failed}` / `session.step.ended` 之后用 `GET /api/session/:id/message/:messageID` 取权威快照,
  整条重发 `message.updated` + `message.part.updated` —— 增量只用来让字一个个出来,内容以 2.x 存储为准。
- **2.x 消息 → v1 `{info, parts}`**:`AssistantText` → `text` part;`AssistantReasoning` → `reasoning`;`AssistantTool{name,state}` → `tool`
  part(`state` 四态对 v1 的 `pending/running/completed/error`,`state.metadata.codepuppyDisplay` 原样搬到 v1 part 的 `display`,I7b);
  `Shell` → v1 的 shell 消息形状;`Compaction` → `compaction` part;`Synthetic`/`System` → v1 的 synthetic text。不认识的类型
  ⇒ 丢弃并 `console.error` 带类型名(不静默)。
- **表外请求响亮失败**:没有 handler 的方法 + 路径 ⇒ 回 `501`,body 是 `{ name: "CodePuppyEngineAdapterUnsupported", data: { method, path } }`,
  同时 `console.error`。冻结代码里 v1 SDK 默认 `throwOnError:false`,调用方拿到 `error`;`throwOnError:true` 的调用抛错。
  这是「到达 2.x 引擎的唯一通路是这张表;其余在适配器里响亮失败」—— 咽喉在,对未知默认拒。
- **对引擎源以外的请求**原样交给 `globalThis.fetch`(按 `new URL(url).origin === engineOrigin` 判)。
- **身份**:适配器不碰口令。按 I8,renderer 只拿到 `{ url }`,`Authorization` 由 main 的 `onBeforeSendHeaders` 补;
  适配器建 `@opencode/client` 时不带认证头。

### 2.7 被否决的替代(各一句)

- **冻结 app/ui 放回 `packages/{app,ui}` 原位**:2.x 工作区装不上(§1.3);要装上就得改 7 个上游包的清单或根 `package.json`,或者造
  空壳的 `@opencode/{ui,app}` 包让上游包解析到假东西。
- **让冻结 app 跑它自带的 v2 路径**:那一支在 0.1.26 里从没跑过,组件读的是另一套 store、还有按协议显隐的元素(§2.2),长相保证不了;
  而且它对的是 1.17.13 的协议,不是 2.2.6。
- **重写数据层为 `@opencode/client/solid`(基线原 §2.6)**:要改冻结 app 的 context 与 renderer 读 store 的全部地方,组件跟着改,违反
  「组件结构不动」。
- **在方法层面手写一个 `OpencodeClient` 替身**:要复刻 hey-api 的结果对象、`throwOnError`、SSE 解析,是「手写别人运行时的替身」;
  路由表方案让这些继续由冻结的生成代码做。
- **在 `Platform.fetch` 之外再猴补 `window.fetch`**:全局副作用、对引擎源以外的请求也生效,判据写不准。
- **复活 v1 引擎包**:违反 ADR-037 决策 5(引擎只有一代)。

## 3. 安全面

- 适配器**不做任何决定**:审批、档位、目录闸都在引擎与 ext(L3/L4);适配器只转形状。不变量:①适配器不改审批请求的 `metadata`(四个冻结键);
  ②不缓存、不重放回复(`permission.reply` 一次请求一次 2.x 调用);③不持有口令(I8)。
- 表外请求一律 501 + 日志,不回退到「猜一个最像的 2.x 端点」。
- 分享入口随 R6 拿掉后,适配器里**没有** `session.share` 的 handler;万一残留调用,得到的是 501,不会把会话发到任何外部地址。

## 11. 仍是推断、没跑过的断言

- 2.2.6 里仍存在的 63 条 `/api/*` 路径与 1.17.13 客户端形状兼容的程度(Q1)。
- 冻结 app 在 `"v1"` 路径下除附件列出的调用外不再打别的引擎路由(抽取是正则 + 人工复核,不是类型分析)。
- Electron `onBeforeSendHeaders` 能给 WebSocket 升级请求补 `Authorization`;本方案让终端改用 2.x 的单次票据,假设 2.x 的终端 WebSocket 只凭票据就放行
  (`v2:packages/protocol/src/groups/pty.ts:115` 的描述如此,没实跑)。
- 用会话事件 + 快照重取派生出的 v1 消息与 0.1.26 的流式观感一致(字一个个出来、工具卡状态切换时机)。
- `@solidjs/router` 等钉回 0.1.26 版本后,与 2.x 根 `overrides` 强制的 `solid-js@1.9.17` 共存无行为差异。
- U2 的合成项目列表字段齐全。
