# 上游更新 runbook:Code Puppy 权威一项不丢

规则在 [ADR-048](../../.claude/rules/adrs/ADR-048-upstream-updates-never-regress-codepuppy-authority.md):
三层权威怎么划、已拿回的权威为什么只许换接法、谁能退役。本文只写每次上游更新前、中、后要做的事。
同步机制本身(信任域、接管清单、合并形状)见 [upstream-integration.md](../architecture/upstream-integration.md)
与 [ci.md](ci.md) §4。

## 什么时候用

| 场景 | 谁做 | 本 runbook 用到哪段 |
| --- | --- | --- |
| 每日同步(`sync-upstream.yml`)自动跑 | 机器 | 只靠登记册测试拦(ADR-048 决定 4);它红了 → 按「中」一段人工处理 |
| 受审上游集成(同步报 `takeover upgrade review required`) | 人 | 前 / 中 / 后 全部 |
| 上游版本或依赖升级 | 人 | 前 / 中 / 后 全部 |
| 引擎换代(ADR-037) | 人 | 前 / 中 / 后 全部,另加 ADR-037 的能力清点 |
| 前端钉版前移(ADR-034 月更 bump) | 人 | 前 / 中 / 后 全部;界面一项是重点 |

登记册(`docs/architecture/codepuppy-authority-registry.*`,`#1666` 交付)落地之前,下文「拉出登记册」一步改为人工汇总三处:
接管清单(`bash scripts/north-star-guard.sh --print-takeover`)、ADR-033 / 035 / 038 / 041 / 042 / 043 各自拿回的决定、
`packages/ext` 与 `packages/ui-mac` 主进程握住的决定。

## 前:列出这次会碰到哪些权威

1. 定本次上游 SHA,算出上游这次改了什么:

   ```bash
   UP=<本次上游 SHA>
   BASE=$(git merge-base origin/alpha "${UP}")
   git diff --name-only --no-renames "${BASE}" "${UP}" -- $(bash scripts/north-star-guard.sh --print-takeover)
   ```

   第二条命令的输出 = 上游改到的接管路径(与同步的 `Takeover intake check` 同一套 pathspec 语义)。空输出不等于没碰到权威:
   L0 握住的权威(插件钩子、配置注入、主进程决定)不在接管清单里,要按下一步逐条对。

2. 拉出登记册,逐条判这次上游改动是否触及它的握法(钩子签名变了、接口改名、文件删除、默认值变了、新开关会绕过它)。
   每条触及的权威写进「权威保持表」(格式见「后」一段),先填前三列。

3. 列出上游这次的新增能力:新工具、新实验开关、新接口、新界面。每项先标记 ADR-048 决定 2 第三层的交界动作(见「中」第 4 步)。

## 中:每一项权威在新上游上怎么握住

1. **逐项写握法。** 权威保持表的每一行都要写「在新上游上怎么握住」和守它的测试名;测试必须带反向臂 —— 拿掉 Code Puppy 的机制、
   让上游默认接管,测试必须红。先跑一次反向臂确认它会红,再跑正向。

2. **只许换接法。** 可以沿 ADR-029 阶梯降到更轻的接缝(L3 → L0),不许交回上游默认。上游删了承载它的文件,就在新上游的对应位置重新拿回。

3. **界面保持当前正式版。**
   - `frontend/frontend-pin.lock` 与 `frontend/codepuppy-patches/codepuppy-frontend.patch` 只为让当前界面连上新引擎而改;
     不因上游前端前进而改长相。
   - 跑 `bash scripts/assert-frontend-patch-roundtrip.sh` 与
     `cd packages/ui-mac && bun test src/renderer/codepuppy-ui/upstream-anchors.test.ts`。
   - 打包后各界面截图,与当前正式版同一界面逐张比对;差异只允许 owner 裁定过的项(写明裁定出处)。
     要比对的界面清单与 `#1668` 方案定的打包版回归截图格相同。

4. **新增能力按交界动作逐项标注。** 每项写清落在哪一类,没有动作的写「无」:

   | 新增能力 | 要在界面出现? → 用 Code Puppy 界面 | 新工具? → 工具身份账本(ADR-041)登记 | 花钱或用凭据? → 经 Code Puppy 平台 | 实验开关? → 保持关,开哪项由 owner 定 |
   | --- | --- | --- | --- | --- |

   上游新界面不直接进;新工具未登记就让它对用户可用,按 ADR-041 是未知身份。

5. **握不住就停。** 任何一项在新上游上握不住(钩子没了、接口不给、只能改上游文件而阶梯又上不去),立即停下,把这一项交 owner:
   哪项权威、为什么握不住、可选做法与用户看到的差别。不先合、不写「后续再补」、不在登记册里自己标退役。

## 后:合并前必须成立

1. 登记册测试绿(本地门);改动若触及每日同步,确认同步候选 job 也跑到了它。
2. 截图比对完成,差异全部有 owner 裁定出处。
3. PR 正文贴「权威保持表」:

   | 权威(登记册条目) | 这次上游改动怎么碰到它 | 原握法 | 新握法(阶梯级 + 位置) | 测试名(含反向臂) | 结果 |
   | --- | --- | --- | --- | --- | --- |

   没碰到任何权威的更新,也要写一行「本次上游改动未触及登记册条目」,并附「前」第 1 步两条命令的输出行数。

## 审查拦截

方案审、代码审按下表逐项核对;命中任何一条直接拦,不进入讨论。

| 形态 | 为什么拦 |
| --- | --- |
| 前端钉版改指与引擎相同的上游 SHA,或前端补丁被清空 / 重生而界面随之改变 | 界面属 Code Puppy 权威,以当前正式版为准 |
| 改用上游界面,或界面与当前正式版不一致且没有 owner 裁定 | 同上 |
| 某项权威「退回上游默认」「交给 OpenCode」,或从登记册 / 接管清单消失而没有新握法与测试 | ADR-048 决定 3 |
| 登记册条目被删除,或被标为退役而没有 owner 原话 | ADR-048 决定 3、4 |
| 新测试没有反向臂,或反向臂没实跑过 | 不会失败的测试不算证据 |
| 上游实验开关被打开而没有 owner 决定 | ADR-048 决定 2 第三层 |

## 反例(形态)

- **「前端跟引擎同一个 SHA」。** 换代方案把前端钉版改指新引擎的上游 SHA、清空 Code Puppy 前端补丁,理由是「前端与引擎同一代次」。
  结果是用户界面换成上游新界面。正确做法:钉版与补丁保持当前正式版,只改让界面连上新引擎的数据与连接层。
- **「能退回 L0 的退回」。** 方案里「先判能不能退回 L0」本意是换更轻的接法,被读成可以把权威交回上游默认,接管清单里的条目随之删除。
  正确做法:退回 L0 之后,这项决定仍由 Code Puppy 做,登记册条目保留,握法改写为 L0 机制,测试带反向臂。
