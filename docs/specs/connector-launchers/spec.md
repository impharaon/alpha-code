# SPEC-connector-launchers｜连接器装上就能启动，连不上时有下一步

用户在定制中心装了连接器，结果一直显示「未能连接」：这些连接器要靠电脑上的 Python 或 Node 工具启动，而普通用户的电脑上没有，或者版本太旧（macOS 自带的 Python 是 3.9.6，这些连接器要 3.10 以上）。这份规格让应用自己带上启动连接器要用的工具，官方目录里的和用户自己加的第三方连接器都适用；仍然连不上时，用户看到的是原因和下一步，不是一句「未能连接」。

## 用户与范围

- 用户：在定制中心安装连接器的用户，电脑上没有装开发工具；连接器来自官方目录，或是用户自己添加的第三方。
- 核心路径：安装一个连接器 → 它启动并连上，用户不用装任何东西。连不上时：应用先处理自己能处理的；需要用户的，写明原因并给一个可点的动作；归不了类的，一键交给对话里的助手排查。
- 包括：
  - 应用自带两种启动器：Python 一侧（uv）和 Node 一侧（npx 一类）。
  - 启动器下载和安装的东西都放在应用自己的数据目录。
  - Python 由启动器自动装一份，版本由应用指定；下载经我们自己的入口。
  - 首次启动时的「正在准备」状态。
  - 连不上时的三步处理。
  - Windows。
- **不包括**：
  - 给每个连接器各带一套运行环境（owner 否定，U-06）。
  - 随应用带 Docker、其它语言的工具链。用到它们的连接器走「写明缺什么」这一步。
  - 改变连接器的权限、写入围栏与联网围栏的规则。
- 假设与依赖：
  - 应用自带的那份 Python（办公连接器用的）不能借给第三方连接器：它带着应用的签名，系统不允许它加载别人的本机模块（实测）。所以另装一份。
  - 香港入口放行 Python 安装包，由 impharaon/alpha-work SPEC-domestic-cloud-connectivity v4 的 BR-09 规定（同日批准）。
  - 连接器自己的包仍从 PyPI、npm 下载，不经香港入口（INT-execution I-18 的三类划分）。
- 范围取舍：
  - Python 一侧用 uv。
  - Node 一侧用官方的 Node 加 npm，不采用 bun：第三方连接器都是按 `npx` 写的，行为完全一致的只有它；bun 更小、启动更快，但试验只验证到握手（讨论 P-05）。
  - 两种启动器都随安装包带，不做成首次使用时下载。

## 体验约定

- 首次启动：定制中心里这个连接器的一行显示「正在准备（首次需要下载运行环境）」和进度；准备期间不算失败，不进入「未恢复的问题」。
- 连不上时，这一行和「未恢复的问题」里的对应条目显示同一句原因和同一个动作（入口的行为按 SPEC-error-message-lifetime，不变）：

  | 情形 | 显示的原因 | 动作 |
  | --- | --- | --- |
  | 下载运行环境或包失败 | 「下载没有完成」加简短原因 | 重试 |
  | 被联网保护拦下 | 「需要你批准联网」 | 打开批准卡片 |
  | 缺少密钥或授权 | 「需要填写密钥」或「需要登录」 | 去填写 / 去授权 |
  | 所在文件夹不符合要求（如 Git 连接器不在仓库里） | 「这个文件夹不是 Git 仓库」 | 换文件夹 |
  | 需要应用没有带的程序（如 Docker、git） | 「需要先安装 Docker」 | 让助手处理 |
  | 启动后崩溃、协议不对等归不了类的 | 「启动失败」，可展开看报错原文 | 让助手排查 |

- 「让助手排查」「让助手处理」：新开一个对话，里面已经带上启动命令、退出码和报错原文，助手直接开始排查。
- 界面：复用定制中心现有的行、状态标记与按钮，以及「未恢复的问题」入口；不新增页面，不另出设计稿。

## 业务规则

- **BR-01** 应用自带 Python 一侧和 Node 一侧的启动器。在没有装任何开发工具的电脑上，官方目录里用这两种启动器的连接器，以及用户自己添加的用这两种启动器的第三方连接器，都能启动 —— I-23（U-06、U-07），P-01、P-03。
- **BR-02** 电脑上没有合适的 Python 时，启动器自动装一份，不需要用户操作；这一份能加载第三方的本机模块 —— I-22（U-07），P-03。
- **BR-03** 启动器下载、安装和缓存的东西（Python、包、缓存）都放在应用自己的数据目录里，在写入围栏内可写 —— I-22，P-01。
- **BR-04** Python 的安装包经我们自己的入口下载，国内不开代理也能下完；入口不可用时自动改从原始来源下载 —— I-23（U-08），P-04；SPEC-domestic-cloud-connectivity。
- **BR-05** 用户电脑上已有的同名工具不影响结果：不管有没有、版本新旧，连接器都能启动 —— P-01。
- **BR-06** 首次启动需要下载时显示「正在准备」与进度，不算失败；网络慢时继续等，不因超过连接时限而判失败 —— P-02。
- **BR-07** 连不上时，应用自己能处理的直接处理，不打扰用户：自动重试、换下载来源、用自带的启动器 —— I-23（U-06），P-02。
- **BR-08** 需要用户的，写明原因并给一个可点的动作，原因与动作按「体验约定」的表 —— I-23（U-06），P-02。
- **BR-09** 归不了类的失败，用户可以一键交给对话里的助手：启动命令、退出码、报错原文一并带过去 —— I-23（U-06「不应该报错了之」），P-02。
- **BR-10** 以上在 Windows 上同样成立 —— impharaon/alpha-work INT-safety U-34「还需要考虑 windows 系统，现在没发 windows 包后续是需要发的」。
- **BR-11** 已经准备好的连接器再次启动不依赖网络：断网或网络很慢时照常连上，启动时间不因网络变长 —— P-05（试验：`npx` 默认每次启动都联系 npm 的服务器，出现过 77 秒）。

## 用户会碰到的限制

## 待决

无。规格批准不等于开发授权；开发未授权。两点没有在本机验证、由技术设计确认，都有退路，不影响上面的验收：随包的启动器带着「允许加载别人签名的本机模块」的权限能否通过应用的正式签名与公证（退路：启动器以原样的压缩包随应用带，首次启动时解到应用数据目录）；真围栏的联网限制下启动器的下载（三种启动器都认代理设置，已实测）。
