# SPEC-project-agent-fields｜项目里给助手写的开关、工具与温度设置都生效

在项目里定义助手(agent)的用户,可以写「停用这个助手」「不许用某个工具」「温度调低」。换到 OpenCode 2 后这几项被我们自己的翻译层悄悄丢掉:写了不报错,也不起作用。本规格让它们重新生效。

## 来源
- 意图 [INT-upstream-upgrade-readiness](https://github.com/impharaon/alpha-work/blob/main/docs/intents/INT-upstream-upgrade-readiness.md) I-12,owner 2026-11-12 批准(U-12「需要查是否有替代方案，tools 等功能 disable temperature 都应该是基础能力吧。」)。
- 现状事实:`engine/1662-opencode2` @ 713727444b 只读盘点(2026-11-12)。
- Story:待建。

## 现状(盘点结论,回答「有没有替代方案」)

| 用户写的 | 现在 | 新引擎自己的对应做法 | 结论 |
| --- | --- | --- | --- |
| `tools: {某工具: false}` | 被丢掉 | 有:新引擎用权限规则表达,读自己的配置文件时会自动把 `tools` 换算成允许/禁止规则 | 有替代,照引擎的换算接上即可 |
| `disable: true` | 被丢掉 | 有:新引擎叫 `disabled`,效果是把这个助手移除 | 有替代,接上即可 |
| `temperature`、`top_p` | 被丢掉 | 引擎会把它挪到一个「请求附加参数」的位置,但盘点没找到任何代码在发请求时读这个位置(推断,未实跑);按模型设置温度是生效的 | 助手级没有现成替代,需要我们在发请求前补上 |
| `steps`、`hidden`、`color`、`variant` | 同样被丢掉 | 都有,引擎原生支持 | 接上即可 |

- 丢失发生在我们自己的 `applyAgents`(`packages/ext/src/engine-transforms.ts`),它只传 prompt、description、mode、model、permission;不是引擎拒收。
- 1.x 上 `disable`、`temperature`、`top_p`、`steps`、`hidden`、`color`、`variant` 都生效;`tools` 在 1.x 上很可能也没生效(推断)。
- **与已批准方案的冲突**:扩展清单方案(`docs/specs/upgrade-extension-manifest/design.md` 准入表)把 permission 以外的这些字段写成「不用,只记一行日志」。owner U-12 认定它们是基础能力,本规格批准后,该表这一格改为「收」,由方案变更流程处理。

## 用户与范围
- 用户:在项目文档里定义或调整助手的用户,以及通过定制中心把助手装到项目里的用户。
- 核心路径:在项目文档里给助手写上述字段 → 打开该项目 → 助手按所写的生效。
- 已先行:`tools`(BR-01、BR-02 及 AC-01 至 AC-03)由 alpha-code#1693 按 owner 2026-11-12「tools 这次修」实现,本规格其余部分待批准。
- 包括:项目文档里助手的 `tools`、`disable`、`temperature`、`top_p`、`steps`(含旧名 `maxSteps`)、`hidden`、`color`、`variant`。
- **不包括**:新增任何字段;改变「项目未获同意时哪些字段不生效」的现有规则以外的权限模型;用户全局配置里的助手(由引擎直接读,不经我们的翻译)。
- 假设与依赖:在 OpenCode 2 换代(alpha-code#1662)合入之后实施;与扩展清单方案(I-06)的实现同批或其后。
- 范围取舍:本期必做 = BR-01 至 BR-05。用户全局配置里助手的 `temperature` 可能同样不生效(推断),后续考虑,见待决。

## 体验约定
不适用(没有界面变化;`hidden`、`color` 影响的是现有助手选择器的既有呈现)。

## 业务规则
- **BR-01 tools 生效**:项目助手的 `tools` 按引擎自己的换算规则变成允许/禁止规则;同一工具上 `permission` 另有写法时以 `permission` 为准 —— I-12。
- **BR-02 放宽权限的写法要项目同意**:`tools` 里写 `true`(允许)会放宽权限,与 `permission`、`model`、`disable`、`mode` 一样,只在用户已同意该项目的扩展内容时生效;未同意时不生效。`tools` 里写 `false`(禁止)只会收紧,同样按此规则处理,保持一条规则 —— 权限不变量:未经同意的项目文档不能放宽权限。
- **BR-03 disable 生效**:项目已获同意且助手写了 `disable: true` 时,该助手不出现在选择器里,也不能被派发 —— I-12。
- **BR-04 temperature、top_p 生效**:使用该助手发起的模型请求带上所写的温度与 top_p;模型不支持温度时不带,不报错 —— I-12;「模型不支持则不带」沿用 1.x 的做法。
- **BR-05 其余字段生效,用不上的有记录**:`steps`、`hidden`、`color`、`variant` 按引擎原生含义生效;本规格之外、引擎也不认识的字段记一行「未应用」日志,不报错 —— I-12;日志做法沿用扩展清单方案。

- **BR-06 写坏的条目整条不应用**:助手条目里任何一个本规格涉及的字段写法不合法时,这个助手条目整条不应用,同一份文档里其他助手照常,结果与引擎读同一份文档时一致 —— 权限不变量:写坏的条目不能比引擎自己读时更宽松。`tools` 与 `permission` 已由 alpha-code#1693 先行实现;其余字段(如 `model`、`mode` 写坏)引擎同样丢整条而我们目前不丢(读代码所得,未实测),由本规格补齐。

## 用户会碰到的限制
无新增。BR-02 是现有「项目未获同意时权限类字段不生效」规则的延伸,用户已在使用同一个同意框。

## 验收
| ID | Given / When / Then | 依据 |
| --- | --- | --- |
| AC-01 | 给定已获同意的项目里一个助手写了 `tools: {bash: false}`;当用这个助手对话并让它执行命令;则命令工具不可用(被拒绝或不在其工具列表里) | BR-01 |
| AC-02 | 给定同一个助手同时写了 `tools: {bash: false}` 和允许 bash 的 `permission`;则以 `permission` 为准,命令可执行 | BR-01 |
| AC-03 | 给定未获同意的项目里一个助手写了 `tools: {某工具: true}`;则该工具不因此被放行,行为与没写一样 | BR-02 |
| AC-04 | 给定已获同意的项目里一个助手写了 `disable: true`;则助手选择器里没有它,派发它的请求失败并说明该助手已停用 | BR-03 |
| AC-05 | 给定一个助手写了 `temperature: 0.2`、`top_p: 0.9`,所用模型支持温度;当用它发一条消息;则发往模型的请求里温度为 0.2、top_p 为 0.9 | BR-04 |
| AC-06 | 给定同样的助手,所用模型不支持温度;则请求里不带温度,对话正常完成 | BR-04 |
| AC-07 | 给定一个助手写了 `steps: 3`;当一次回答需要超过 3 步;则在第 3 步后停止并按引擎现有方式收尾 | BR-05 |
| AC-08 | 给定一个助手写了 `hidden: true`、`variant`、合法的 `color`;则它不出现在选择器里但仍可被派发,请求使用所写的模型变体,颜色按所写显示 | BR-05 |
| AC-10 | 给定一个助手的 `mode` 或 `model` 写法不合法、同时写了放宽权限的 `permission`;则该助手条目整条不应用,文档里其他助手照常 | BR-06 |
| AC-09 | 给定一个助手写了引擎不认识的字段;则项目正常加载,日志里有一行指出该字段未应用 | BR-05 |
